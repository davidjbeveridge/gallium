WEB TASK ENGINE FOR AI AGENTS

A better route through the web.

Gallium is a standalone engine that takes a web goal, chooses how to reach it, and adapts to what it finds. It brings back a source passage or checks that a configured change took effect.

Runs locally through the CLI or MCP.

From a goal to evidence.

Driving a browser one action at a time leaves the agent to decide what to click, when to wait, and whether the job is done. Gallium handles that loop inside one task request. When a document has the answer, it can fetch the text directly.

“What does status 418 mean?”

  1. Fetch the source. A direct HTTPS request gets the text of RFC 2324.
  2. Select the passage. The model picks from excerpts in the document.
  3. Return the evidence. Gallium includes the source URL and a hash of the passage.

“Start the example and report the greeting when it loads.”

  1. Open a task tab. An explicit UI request goes straight to the live page.
  2. Act on what’s visible. Gallium selects Start, then waits when it sees a loading indicator.
  3. Check again. It finds the greeting, confirms it is still in the live DOM, and closes its tab.

Inside the engine.

CLI and MCP clients share one local service per state directory. Its task controller makes routing decisions, adapters execute them, and a SQLite journal records what happened.

Pick a route.

For a public URL, Gallium assesses the goal and tries HTTPS when document text could answer it. Missing evidence or certain fetch failures can move the task to live exploration. An explicit request to use the interface starts there.

For a configured task, Gallium filters procedures by scope and input. Jev, the model, makes one structured assessment of which candidates fit the goal. Code picks an eligible procedure in the following order and keeps it for that operation.

  1. Direct HTTP request
  2. Request inside the signed-in browser session
  3. Browser interaction

Observe, act, and check.

Gallium observes visible controls and passages. Jev can select an observed control, identify a loading state, or point to a passage that answers the question. The engine validates the selection, acts, and looks again.

Public exploration stays on the same origin. It runs for up to 12 decision steps or 60 seconds and stops when the next action has an unclear effect. Gallium rechecks the chosen passage in the live page before returning it. Jev assesses relevance.

Configured procedures can use deterministic steps or a structured model decision. The procedure defines a separate check for the actual result.

Read the exploration loop ↗

Carry forward the right state.

Feedback drives the next move within a task. Across runs, the journal remembers the selected procedure, verified outcomes, and writes with uncertain effects. If a save may have gone through, Gallium checks the resulting state before any retry.

Today’s route preference follows a fixed policy. Gallium records model latency and reported cost for evaluation. Learned route ranking is a research direction in the architecture roadmap.

Read the journal schema ↗

Keep control with the person.

Independent HTTP work can run in parallel. Browser work and work on the same account run in queues. If ownership changes while a task is waiting, the engine discards the stale request.

Pause a configured browser workflow to take over. Gallium confirms its debugger has detached and keeps the pause through restarts. After explicit handback, it checks whether you already finished the task.

Run Gallium locally.

Start with Git and Node.js 24 or later. The demo runs in a temporary fixture. The full install adds the CLI and routing skill from this repository.

Install the engine.

The installer registers the MCP server when the Codex CLI is available. Already cloned the repo for the demo? Start at npm ci.

Terminal
git clone https://github.com/davidjbeveridge/gallium.git &&
cd gallium &&
npm ci &&
npm run install:local

Try the demo.

Watch Gallium verify a save, skip a duplicate, and keep a human pause through a restart. The fixture needs only Git and Node.

Terminal
git clone https://github.com/davidjbeveridge/gallium.git &&
cd gallium &&
npm run demo

Make your first public lookup.

Set up the Jev router first. This lookup reads an RFC directly over HTTPS. For tasks that use the live interface, connect the Chrome bridge.

Terminal
~/.local/bin/gallium task --operation rfc418 \
  --goal 'What does HTTP status 418 mean in this document?' \
  --target https://www.rfc-editor.org/rfc/rfc2324.txt

Send the same goal over MCP

Call web_task with a stable operation ID, the goal, and the public URL.

{
  "operationId": "rfc418",
  "goal": "What does HTTP status 418 mean in this document?",
  "target": "https://www.rfc-editor.org/rfc/rfc2324.txt"
}

Before you connect.

Which browser does Gallium use?

Direct HTTP runs without a browser. For browser-session requests and live UI tasks, the current adapter uses installed desktop Chrome through a separately enabled bridge.

What can it do on a site I’m signed into?

Configure a procedure with the account, allowed actions, and the state Gallium should verify. Browser-session requests use the session in the enabled tab. Public exploration stops at sign-in or challenge pages.

When do I need a model provider?

Public tasks and goal-based procedure matching use a configured Jev router through OpenRouter System One. Deterministic procedures and the local demo can run without a model call.

What leaves my machine?

The engine and its journal run locally. When a task uses the configured router, Gallium sends the goal and relevant excerpts, controls, or nonsecret procedure details to the model provider. Browser-session requests use cookies and CSRF tokens inside the tab.

Can I use another MCP client?

Gallium exposes a stdio MCP server. Configure your client to launch node bin/mcp.mjs from the checkout. Use web_task for a goal, web_status for receipts, and web_control for pause and handback.
